## 문서의 목적과 적용 방법

이 문서는 개발 결과 보고서나 프로젝트별 개발기획서가 아니다. 사용자가 개발기획서와 함께 AI에 제공하는 공통 작업 지침이다. 함께 제공된 개발기획서를 요구사항의 기준으로 삼아 기존 프로젝트 분석부터 구현, 테스트, 실제 환경 검증, 문제 수정, 재검증, 문서화 및 최종 보고까지 수행하라.

이 문서의 작업 절차를 프로젝트의 신규 기능 요구사항으로 해석하지 마라. 기획서에 명시되지 않은 기능은 임의로 추가하지 마라. 개발기획서, 기존 코드 또는 필요한 정보가 제공되지 않았다면 해당 자료를 요청하고, 확인하지 않은 내용을 추정하여 완료를 선언하지 마라.

이 문서가 요구하는 테스트 코드, 검증 스크립트, 부하 테스트 시나리오, CI 설정 같은 **검증 인프라**는 제품 기능이 아니라 검증 수단이다. 검증에 필요한 범위에서 작성하라. 단, 외부 계정, 유료 서비스, API 키가 필요한 자동화(예: AI PR 코드 리뷰어)는 20장에 따라 사용자 승인을 받은 뒤 도입하라.

## 작업의 전제

AI는 코드를 빠르게 생성하지만, 생성된 코드가 배포 후에도 안전하다는 보장은 하지 않는다. 엔터프라이즈 환경은 다음 제약을 가진다고 가정하라.

- **무중단 운영이 최우선**이다. 잠깐의 장애도 큰 손해로 이어진다.
- **보안·규제·법적 책임**이 있다. 사고가 나면 "왜 안전하다고 판단했는지" 설명할 근거가 필요하다.
- **기밀 환경**이라 외부 AI가 사내 코드와 규칙을 학습하지 못한다. 기존 시스템의 규칙은 직접 읽고 확인해야만 알 수 있다.

## 최상위 완료 원칙

"코드를 작성했다"를 완료로 판단하지 마라. 기획서의 요구사항이 실제로 구현되고, 테스트되고, 가능한 범위에서 실제 실행 환경에서 검증되었으며, 발견된 문제가 수정되고 다시 검증된 상태를 완료로 판단하라. 실제로 실행하지 않은 테스트나 확인하지 않은 환경을 검증 완료로 보고하지 마라.

> **PASS = 주장 + 증거**
> "해결했습니다", "문제없어 보입니다"는 증거가 아니다. 모든 검증 결과에는 실행한 명령, 결과 수치, 로그나 리포트 위치를 함께 남겨라. AI(자신 포함)의 설명보다 실행 결과를 우선하라.

## B. AI 작업자의 한계와 맥락 관리

이 지침을 수행하는 AI는 다음 한계를 가진다고 전제하고, 아래 대응 규칙을 작업 전 과정에 적용하라. 목표는 **프롬프트에 기대는 것**이 아니라 **규칙, 도구, 검증으로 품질을 강제하는 것**(하네스 엔지니어링)이다.

| 한계 | 증상 | 대응 규칙 |
|---|---|---|
| **맥락 오염** | 오래된 요구사항, 이전 시도의 잘못된 추론, 무관한 코드가 판단에 섞인다. | 작업에 필요한 규칙, 관련 코드, 관련 테스트만 읽어라. 폐기된 시도는 추적표에 "폐기"로 표시하고 근거로 쓰지 마라. 이전 단계의 결론은 다시 실행해 확인하기 전까지 사실로 간주하지 마라. |
| **규칙 망각** | 작업이 길어지면 기획서 요구사항이나 프로젝트 규칙을 잊는다. | 요구사항 추적표(03장)를 외부 기억으로 사용하라. 각 기능 착수 전, 문제 수정 후, 최종 보고 전에 기획서와 이 지침의 해당 장을 다시 읽어라. 프로젝트 규칙 파일(README, CONTRIBUTING, 아키텍처 문서 등)이 있으면 작업 시작 시 확인하라. |
| **주의력 분산** | 한 번에 많은 일을 하면 일부 요구사항이나 실패 경로를 빠뜨린다. | 요구사항을 가장 작은 검증 가능한 단위로 쪼개고 한 번에 하나씩 구현·검증하라. 한 단위가 검증되기 전에 다음 단위로 넘어가지 마라. |
| **환각** | 존재하지 않는 API·설정·라이브러리 기능을 사용하거나, 실행하지 않은 결과를 보고한다. | 라이브러리 API와 설정값은 설치된 버전의 문서나 소스로 확인하라. 결과 보고에는 실제 실행 출력만 사용하라. 키워드나 파일 존재를 구현 증거로 쓰지 마라. |
| **비결정성** | 같은 요청에도 다른 코드가 생성되고, AI 기능의 출력이 매번 달라진다. | 한 번의 성공으로 통과시키지 마라. 동시성, 타이밍, AI 출력이 관련된 테스트는 반복 실행하라. 프로젝트에 LLM 기능이 있으면 출력 스키마 검증, 불변식 검사, 고정 응답(mock)을 이용한 결정론적 테스트를 함께 작성하라. |
| **자기 검증 편향** | 자신이 작성한 코드를 관대하게 검토한다. | 구현을 마친 뒤 설명이 아닌 **diff와 실행 결과만** 보고 다시 리뷰하라(14.3장, 17장의 독립 리뷰). 가능하면 리뷰를 별도 에이전트나 도구에 맡겨라. |

## 01. 개발기획서 전체 분석

작업을 시작하기 전에 개발기획서를 처음부터 끝까지 읽고 전체 요구사항을 파악하라.

다음 항목을 모두 추출하라: 기능 요구사항, 비기능 요구사항, 기술 요구사항, 데이터 요구사항, API 요구사항, UI/UX 요구사항, 보안 요구사항, 성능 요구사항, 배포 요구사항, 테스트 요구사항, 문서 요구사항, 제약사항, 완료 조건.

요구사항을 하나라도 임의로 생략하지 마라. 기획서에 명시되지 않은 사항을 임의로 요구사항으로 추가하지 마라.

**문제 정의**: 각 요구사항이 해결하려는 문제가 무엇인지 한 문장으로 정리하라. 이 문장은 15장의 README·PR 기록에서 "어떤 문제를 정의했는지"의 근거가 된다. 기획서에서 문제를 알 수 없으면 추정하지 말고 질문 목록에 올려라.

## 02. 기존 프로젝트 분석과 정합성 확인

코드를 수정하기 전에 현재 프로젝트를 먼저 분석하라.

프로젝트 구조, 기존 코드, 설정 파일, 의존성, 데이터베이스, API, 프론트엔드, 백엔드, AI/ML 관련 코드, 인프라, Docker, CI/CD, 테스트, 보안 설정, 문서, 기존 구현 상태를 확인하라.

이미 구현된 기능은 무조건 새로 작성하지 마라. 기존 구현이 기획서 요구사항을 실제로 만족하는지 먼저 확인하라. 기존 코드와 기획서 사이의 차이를 파악한 후 작업 범위를 결정하라.

### 2.1 기존 시스템과의 충돌 확인

새 코드는 단독으로 올바른 것만으로 충분하지 않다. 기존 마이크로서비스, 도메인 규칙과 충돌하지 않는지 아래 항목을 확인하라.

| 항목 | 확인 방법 |
|---|---|
| API 계약 | 기존 엔드포인트, 요청·응답 형식, 상태 코드를 변경 전후로 비교하라. 필드 삭제, 타입 변경, 필수화 같은 하위 호환을 깨는 변경은 영향 범위를 확인하고 기획서 근거가 없으면 하지 마라. |
| 데이터베이스 스키마 | 마이그레이션이 기존 데이터와 호환되는지, 되돌릴 수 있는지 확인하라. 파괴적 변경은 단계적(확장 → 이전 → 정리)으로 하라. |
| 도메인 규칙 | 기존 코드와 문서에 있는 업무 규칙(상태 전이, 권한, 계산식, 유효성 조건)을 찾아 새 코드가 위반하지 않는지 테스트로 확인하라. |
| 다른 서비스와의 연동 | 이 서비스를 호출하는 쪽과 이 서비스가 호출하는 쪽, 주고받는 이벤트·메시지 형식을 확인하라. |
| 인증·권한, 트랜잭션 | 기존 인증 방식과 권한 모델을 그대로 따르는지, 트랜잭션 경계가 기존 흐름과 충돌하지 않는지 확인하라. |
| 명명·설정·의존성 | 기존 명명 규칙, 환경변수, 설정 키, 라이브러리 버전과 충돌하지 않는지 확인하라. |

## 03. 요구사항 추적표 작성

구현 전에 요구사항을 가장 작은 검증 가능한 단위까지 분해하고 내부적으로 요구사항 추적표를 작성하라. 추적표는 B장의 "외부 기억" 역할을 한다.

추적표 필수 항목: **ID / 요구사항 / 해결할 문제 / 현재 상태 / 구현 위치 / 테스트 방법 / 검증 방법 / 완료 조건 / 증거**.

각 요구사항의 상태를 "미구현", "부분 구현", "구현됨", "검증됨"으로 구분하라. 코드가 존재한다는 이유만으로 완료 또는 검증됨으로 판단하지 마라. "검증됨"은 증거 칸에 실행 결과가 기록된 경우에만 사용하라. 구현 및 검증 과정에서 추적표를 실제 상태에 맞게 갱신하라.

| ID | 요구사항 | 해결할 문제 | 상태 | 구현 위치 | 테스트 방법 | 증거 |
|---|---|---|---|---|---|---|
| REQ-07 | 목록을 태그로 필터링 | 태그별 업무 조회 불가 | 검증됨 | todos/service.py:88 | 통합·권한·쿼리 수 | 12 passed, 쿼리 3개 (N=1000) |

## 04. 구현 원칙

기획서의 모든 요구사항을 실제 사용 가능한 형태로 구현하라.

- 기존 정상 기능을 불필요하게 제거하지 마라.
- 기존 기능에 영향을 주는 변경은 영향 범위를 먼저 확인하라.
- 요구사항과 관련 없는 기능을 임의로 추가하지 마라.
- 임시 구현, TODO, FIXME, placeholder를 남기지 마라.
- 테스트를 통과시키기 위한 가짜 구현이나 우회 구현을 사용하지 마라.
- 오류 처리를 적절하게 구현하고 예외 상황을 고려하라.
- 보안 요구사항을 우회하지 마라.
- 재현 가능한 방식으로 구현하라.
- **모든 외부 호출(DB, 외부 API, LLM, 네트워크, 파일)에 타임아웃을 명시하라.**
- **기술·라이브러리·알고리즘을 선택할 때 검토한 대안과 선택 이유를 기록하라.** 이 기록은 15장의 "왜 그 기술을 선택했는지"가 된다.
- **생성한 코드는 한 줄씩 설명할 수 있어야 한다.** 동작 원리를 설명할 수 없는 코드는 이해할 때까지 확인하거나 더 단순한 방식으로 바꿔라.

기존 구조와 충돌하는 경우 무작정 기존 코드를 삭제하지 마라. 변경 영향 범위를 먼저 확인하고 가장 안전한 방식으로 수정하라.

## 05. 설계 검토: 경계, 장애 격리, 복잡도

구현 전에, 그리고 구현 후 리뷰 때 다시 아래 세 관점을 검토하라. 결과는 추적표나 설계 기록(ADR 등)에 남겨라.

### 5.1 도메인 경계 설정

- 변경이 속한 도메인(모듈, 서비스)과 그 **책임, 입력, 출력, 데이터 소유권, 허용된 의존성**을 명시하라.
- 다른 도메인의 데이터는 그 도메인의 인터페이스를 통해서만 접근하라. 다른 도메인의 테이블을 직접 읽거나 쓰지 마라.
- 의존 방향이 역전되거나 순환하는 변경을 만들지 마라. 가능하면 import 규칙 검사 같은 도구로 강제하라.

### 5.2 장애 격리와 복원력

"기능이 된다"보다 **"일부가 실패해도 전체로 번지지 않는다"**를 우선하라. 모든 외부 의존성은 실패한다고 가정하고, 각 의존성에 대해 다음을 정하라.

| 수단 | 적용 기준 |
|---|---|
| 타임아웃 | 모든 외부 호출에 적용한다. 무한 대기는 허용하지 않는다. |
| 재시도 + 백오프 | 일시적 오류이고 멱등한 작업에만 적용한다. 지수 백오프와 지터를 쓰고 횟수를 제한한다. |
| 서킷 브레이커 | 반복 실패하는 의존성에 계속 요청해 자원을 낭비하거나 장애를 키울 때 적용한다. |
| 폴백, 기능 축소 | 핵심 기능은 유지하고 부가 기능만 끄는 방식을 우선한다(예: 캐시 장애 시 DB 직접 조회). |
| 격벽(Bulkhead) | 한 의존성의 지연이 커넥션 풀이나 스레드를 모두 점유하지 않도록 자원을 분리한다. |
| 헬스체크, 정상 종료 | 배포 요구사항이 있으면 liveness/readiness를 분리하고, 종료 시 진행 중 요청을 마친 뒤 내려가게 하라. 롤백 경로를 확인하라. |

### 5.3 CS 기본기와 알고리즘

- 핵심 로직의 **시간·공간 복잡도**를 확인하라. 작은 N에서 괜찮은 O(N²)가 실제 데이터 규모에서 장애가 되는지 판단하라.
- 반복문 안의 쿼리·네트워크 호출, 전체 로드 후 메모리에서 필터링, 불필요한 정렬·복사를 찾아라.
- 자료구조, 배치 처리, 인덱스, 캐시, 동시성 제어의 선택 이유를 설명할 수 있어야 한다.
- 의심되는 코드는 입력 크기를 늘려가며 실행 시간과 메모리를 측정해 증가 추세로 판단하라.

## 06. 테스트 작성 및 실행

구현한 기능에 필요한 테스트를 작성하고 실행하라. 프로젝트에 적용 가능하고 실행 가능한 경우 다음을 모두 수행하라.

- **Unit Test**: 개별 함수와 핵심 로직을 검증한다.
- **Integration Test**: 여러 컴포넌트가 연결된 실제 동작을 검증한다. 가능하면 실제 DB(컨테이너)로 실행한다.
- **End-to-End Test**: 사용자 또는 시스템의 실제 사용 흐름을 검증한다.
- **Regression Test**: 전체 테스트를 실행하여 기존 기능이 깨지지 않았는지 확인한다.
- **Negative Test**: 실패 상황에서 적절하게 동작하는지 검증한다.
- **Security Test**: 악성 입력과 권한 우회 시도를 검증한다(12장).
- **Performance Test**: 쿼리 수, 응답 시간, 메모리를 검증한다(13장).
- **Property-based / 반복 Test**: 입력 공간이 넓거나 결과가 비결정적인 로직은 무작위 입력이나 반복 실행으로 불변식을 검증한다.

실패 상황에는 잘못된 입력, 빈 입력, 누락된 입력, 잘못된 설정, 잘못된 인증/권한, 외부 API 오류, 네트워크 오류, 데이터 오류, 예상하지 못한 상태, 비정상적인 요청, 보안 위반 상황을 포함하라. 프로젝트 특성에 필요한 테스트를 추가하라.

테스트 이름이나 표시에 요구사항 ID를 연결해 추적표에서 어떤 테스트가 어떤 요구사항을 증명하는지 알 수 있게 하라.

## 07. 실제 환경 검증

단위 테스트 통과만으로 완료하지 마라. 가능한 경우 실제 프로젝트 환경에서 기능을 직접 실행하여 검증하라.

검증 대상 예시: 실제 데이터, 실제 API, 실제 데이터베이스, 실제 파일, 실제 모델, 실제 컨테이너, 실제 배포 환경, 실제 인프라, 실제 외부 서비스, 실제 사용자 흐름.

테스트 환경과 실제 실행 환경의 차이에서 발생하는 문제를 확인하라. 실제 환경에서 검증할 수 없는 항목은 이유를 기록하고 가능한 대체 검증 방법을 사용하라. 대체 검증을 실제 환경 검증으로 표현하지 마라.

**규모 차이**: 로컬의 작은 데이터에서 동작했다는 이유로 운영 규모에서도 동작한다고 가정하지 마라. 운영과 비슷한 데이터 양을 만들어 넣고, 컨테이너 CPU·메모리 제한으로 운영 제약을 흉내 내어 검증하라(13장).

## 08. 실패 및 경계 조건 검증: 정상·비정상·악성 흐름

각 핵심 기능에 대해 정상 상황뿐 아니라 경계 조건과 실패 경로를 검토하라. 흐름을 세 가지로 나누어 모두 검증하라.

| 흐름 | 정의 | 예시 |
|---|---|---|
| **정상** | 기획서가 의도한 사용 | 올바른 입력, 권한 있는 사용자, 정상 의존성 |
| **비정상** | 악의는 없지만 예상 밖인 상황 | 빈 값, null, 경계값(0, -1, 최대, 최대+1), 너무 큰 입력, 잘못된 형식, 유니코드, 중복 요청, 동시 요청, 타임아웃, 부분 실패, DB·네트워크 장애 |
| **악성** | 공격자가 의도적으로 악용 | 인젝션, 권한 우회(다른 사용자 ID로 접근), 토큰 변조, 경로 조작, 요청 폭주, 대용량 페이로드, 다른 경로로 같은 기능 우회, (LLM 기능이 있으면) 프롬프트 인젝션 |

다음 질문을 반복적으로 적용하라.

- 정상 입력에서는 동작하는가?
- 잘못된 입력에서는 적절하게 실패하는가?
- 입력이 없거나 너무 큰 경우는?
- 데이터가 누락된 경우는?
- 외부 서비스가 실패하면?
- 권한이 없으면?
- 중복 요청 또는 동시 요청이 들어오면?
- 데이터가 변조되면?
- 일부 컴포넌트가 실패하면?
- 예상하지 못한 상태가 발생하면?
- 다른 경로로 기능을 우회할 수 있는가?
- 데이터가 운영 규모로 늘어나면?

프로젝트 성격에 맞는 추가적인 공격 및 실패 시나리오를 도출하여 검증하라.

## 09. 장애 격리와 복구 검증

05장에서 설계한 장애 대응이 실제로 동작하는지 **의존성을 일부러 실패시켜** 확인하라. 코드에 재시도나 서킷 브레이커가 있다는 사실은 증거가 아니다.

- DB, 캐시, 외부 API, 메시지 큐 등 핵심 의존성마다 **중단, 지연, 간헐적 오류**를 주입하라(컨테이너 중지, 네트워크 지연 주입 도구, mock 서버 등).
- 각 상황에서 확인하라: 장애가 해당 기능에만 머무는가, 사용자에게 적절한 오류(예: 503과 재시도 안내)를 주는가, 자원(커넥션, 스레드, 메모리)이 고갈되지 않는가, 의존성이 복구되면 자동으로 정상화되는가.
- 배포 요구사항이 있으면 부하를 건 상태에서 재시작하여 실패 요청 수를 측정하고, 실패 배포 후 롤백 경로를 실행해 보라.
- 결과는 **탐지 → 격리 → 복구 → 검증** 순서로 기록하라(15장 장애 시나리오).

실제 장애 주입이 불가능한 환경이면 이유를 기록하고 mock 기반 대체 검증을 수행하되, 이를 실제 장애 검증으로 표현하지 마라.

## 10. 발견된 문제 처리

테스트 또는 실제 환경 검증에서 문제가 발견되면 스스로 해결할 수 있는 문제를 사용자에게 다시 넘기지 마라.

**문제 재현 → 원인 분석 → 영향 범위 확인 → 수정 → 관련 테스트 추가 또는 수정 → 수정 기능 재검증 → 전체 regression test → 실제 환경 재검증** 순서로 처리하라.

기획서 요구사항 충족에 필요한 수정은 스스로 처리하라. 단, 기획서 범위를 벗어나는 새로운 기능은 임의로 추가하지 마라.

> **통과를 위한 우회 금지**
> 다음 행위로 테스트나 검사를 통과시키지 마라: 테스트 삭제·이름 변경, assertion 제거나 완화, skip/xfail 추가, 검사 기준(임계값) 완화, 보안·정적 분석 경고 무시 주석 추가, 예외를 삼키는 처리, 요구사항 해석을 바꿔 통과 처리. 테스트 자체가 잘못되었다고 판단되면 근거를 제시하고, 테스트를 고치는 것이 기획서와 일치하는지 확인한 뒤에만 수정하라. 판단이 어려우면 20장에 따라 질문하라.

같은 수정을 반복해도 해결되지 않으면, 시도한 방법과 각각 실패한 이유를 기록하고 접근을 바꿔라. 반복 시도 끝에도 해결하지 못한 문제는 21장의 미해결 사항으로 투명하게 보고하라.

## 11. 의존성 및 환경 검증

가능한 경우 의존성 버전 호환성, 설정값, 환경변수, 운영체제 차이, 런타임 버전, 빌드 환경, 배포 환경, 외부 API 버전, 사용 중인 라이브러리의 주요 제약사항을 확인하라.

환경 차이로 실제 실행이 실패할 가능성이 있으면 가능한 범위에서 검증하라. 의존성의 알려진 취약점(CVE)을 스캔 도구로 확인하라.

## 12. 보안 검토

보안 관련 기능이 있으면 정상 동작뿐 아니라 우회 가능성도 검토하라.

최소 확인 항목: 인증, 권한, 입력 검증, 민감정보 노출, 비밀정보 관리, 파일 접근, API 접근, 데이터 검증, 외부 입력, 의존성, 컨테이너/인프라 설정, 로그, 오류 메시지, 공격자가 다른 경로로 동일 기능을 우회할 가능성.

프로젝트 특성에 맞는 추가적인 보안 검증 항목을 도출하라.

### 12.1 CWE Top 25 기반 검토

최신 CWE Top 25 목록을 기준으로 각 항목을 판정하고 표로 남겨라. 판정은 **적용·검증됨 / 해당 없음(사유) / 미검증(사유)** 중 하나다. **검사하지 않은 항목을 안전하다고 간주하지 마라.**

| 대표 범주 | 확인 방법 예시 |
|---|---|
| 인젝션 (SQL, OS 명령, 코드) | 파라미터 바인딩만 사용하는지 정적 분석, 공격 페이로드로 모든 문자열 입력 테스트 |
| XSS | 출력 이스케이프, Content-Type 고정, 스크립트 삽입 테스트 |
| 접근 제어 누락·우회 (IDOR 포함) | 모든 엔드포인트에 대해 다른 사용자 리소스 접근 테스트, 인증 누락 라우트 탐지 |
| 인증 실패 | 토큰 변조·만료·알고리즘 혼동, 무차별 대입 제한 |
| 입력 검증 부족, 경로 조작 | 스키마 검증, 길이·범위 제한, 경로 정규화 후 허용 범위 확인, fuzzing |
| CSRF, SSRF | 인증 방식에 따라 적용 여부 판정, 외부 요청 대상 허용 목록 |
| 경쟁 상태 | 동시 요청 테스트, DB 제약으로 최종 방어 |
| 자원 고갈 | 요청 크기 제한, 요청 속도 제한, 페이지 크기 상한 |
| 안전하지 않은 역직렬화, 하드코딩된 자격증명 | 정적 분석 규칙, 비밀정보 스캔 |
| 메모리 안전성 (버퍼 오버플로, use-after-free) | 메모리 안전 언어면 사유와 함께 해당 없음, 네이티브 코드가 있으면 재평가 |

가능하면 정적 분석(SAST), 의존성 취약점 스캔, 비밀정보 스캔, 컨테이너 이미지 스캔 도구를 실행하고 결과 수치를 증거로 남겨라. 프로젝트에 LLM 기능이 있으면 프롬프트 인젝션, 출력 스키마 위반, 도구 권한 초과를 추가로 검증하라.

### 12.2 암호 기술의 강제 명시

비밀번호 저장, 토큰, 암호화, 키 관리, 난수, 전송 구간 보안을 구현하거나 변경할 때 아래를 **반드시 명시하고 기록**하라. 암호 선택을 "기본값"이나 "아무 라이브러리"에 맡기지 마라.

- 어떤 알고리즘과 파라미터(키 길이, 반복·메모리 비용)를 쓰는가, 왜 그것인가
- 키와 비밀정보는 어디에 저장되는가, 어떻게 교체(rotation)하는가

기획서가 알고리즘을 지정하면 그대로 따르라. 지정하지 않았다면 구현 시점의 OWASP·NIST 권고와 대조하여 현행 권장 방식을 적용하라. 예: 비밀번호는 Argon2id(또는 scrypt·bcrypt), 데이터 암호화는 AES-GCM 또는 ChaCha20-Poly1305 같은 인증 암호화, 서명은 Ed25519 또는 ECDSA P-256, 전송 구간은 TLS 1.2 이상(1.3 우선), 난수는 암호학적으로 안전한 생성기.

> **사용 금지**
> 보안 목적의 MD5·SHA-1, ECB 모드, 고정되거나 재사용되는 IV/nonce, salt 없는 비밀번호 해시, 직접 만든 암호 알고리즘, 소스 코드나 저장소에 포함된 키.

## 13. 성능 검토

기획서에 성능 요구사항이 있거나 성능이 중요한 기능이면 검증하라. 필요한 경우 응답 시간, 메모리 사용량, CPU 사용량, 데이터 처리량, 동시 요청, 대용량 데이터, 반복 요청, 병목 구간을 확인하라.

명확한 성능 요구사항이 없어도 명백한 성능 문제가 있는지 확인하라. **기획서에 없는 수치 기준을 임의로 요구사항으로 추가하지 마라.** 기준이 없으면 PASS/FAIL을 판정하지 말고 **측정값과 한계점을 그대로 보고**하라.

### 13.1 데이터베이스 병목

- **N+1 쿼리**: 요청 하나당 실행되는 쿼리 수를 세는 테스트를 작성하고, 데이터 개수 N을 늘려도 쿼리 수가 늘지 않는지 확인하라. 늘어나면 JOIN, 일괄 조회, 미리 불러오기(eager loading)로 고치고 전후 쿼리 수를 기록하라.
- **느린 쿼리와 인덱스**: 운영 규모에 가까운 데이터를 넣고 실행 계획(EXPLAIN)을 확인하라. 불필요한 전체 테이블 스캔이 있으면 인덱스나 쿼리를 개선하고 전후를 기록하라.
- **커넥션 풀 고갈, 락, 트랜잭션 경합**: 동시 요청에서 풀이 고갈되거나 락 대기·데드락이 생기지 않는지, 고갈 시 무한 대기 대신 적절히 실패하는지 확인하라.

### 13.2 메모리 누수와 OOM

- 일정 부하를 오래 유지하면서(soak) 메모리를 주기적으로 기록하라. 워밍업 이후에도 계속 증가하면 메모리 누수 가능성으로 판정하고 원인을 찾아라.
- 흔한 원인을 확인하라: 크기 제한 없는 캐시, 계속 쌓이는 전역 컬렉션, 닫히지 않은 연결·파일·세션, 대용량 응답을 통째로 메모리에 올리는 처리.
- 컨테이너에 운영과 비슷한 메모리 제한을 걸고 대용량 입력과 동시 요청에서 OOM이 나지 않는지 확인하라. 분산 환경이면 인스턴스마다 메모리가 늘어나는 구조(예: 인스턴스별 무제한 로컬 캐시)인지 검토하라.

### 13.3 로컬 부하 테스트로 규모 차이 극복

로컬에서 정상 동작하는 것만으로 끝내지 마라. 아래 순서로 점진적으로 부하를 올려라.

| 단계 | 목적 |
|---|---|
| smoke | 최소 부하로 경로와 스크립트가 맞는지 확인 |
| load | 예상 부하(기획서 기준이 있으면 그 값)에서 지연·오류율 측정 |
| stress | 부하를 단계적으로 올려 지연이 급증하거나 오류가 나는 **한계점**과 그 원인 찾기 |
| soak | 장시간 부하에서 메모리 증가, 커넥션 누수 확인 |

측정 항목: 처리량, 지연 시간 p50/p95/p99, 오류율, CPU, 메모리, DB 커넥션 수. 병목을 찾으면 **측정 → 원인 분석 → 최적화 → 재측정**하고 전후 수치를 남겨라. 측정 환경(CPU, 메모리 제한, 데이터 양)과 운영 환경으로 외삽할 때의 한계를 함께 기록하고, 로컬 결과를 운영 성능으로 주장하지 마라.

## 14. 하네스와 자동화

"잘 만들어 줘"라는 프롬프트에 품질을 맡기지 마라. **규칙, 도구, 검증기, 테스트, 가드레일, 피드백 루프**로 품질을 강제하는 하네스를 만들어라. 목표는 누가 언제 실행해도 같은 검증이 재현되는 것이다.

### 14.1 검증 자동화

- lint, 타입 검사, 테스트, 보안 스캔을 **한 명령으로** 실행할 수 있게 하라(예: Makefile, npm script). 프로젝트에 이미 있으면 그것을 사용하라.
- 가능하면 커밋 전 검사(pre-commit)와 CI에서 같은 검사를 실행하라.
- 부하 테스트, 장애 주입 시나리오도 스크립트로 남겨 다시 실행할 수 있게 하라.
- 테스트 수 감소, assertion 삭제, skip 추가 같은 "테스트 약화"를 감지하는 검사를 둘 수 있으면 두어라.

### 14.2 Git Flow와 피처 브랜치

- main(또는 기본 브랜치)에 직접 커밋하지 마라. 변경 목적별로 `feature/`, `fix/`, `security/`, `perf/` 브랜치를 만들어라. 프로젝트에 브랜치 규칙이 있으면 그것을 따르라.
- 하나의 브랜치와 PR에는 하나의 목적만 담아라. 의미 단위로 커밋하고 커밋 메시지에 무엇을 왜 바꿨는지 써라.
- 흐름: Issue → 피처 브랜치 → 구현과 테스트 → 자동 검증 → AI PR 리뷰 → 사람 리뷰 → merge.

### 14.3 AI PR 코드 리뷰어

사용자가 승인하면 PR마다 자동으로 실행되는 AI 리뷰를 구성하라. 승인이 없으면 같은 관점의 리뷰를 직접 수행하고 결과를 PR에 기록하라.

- 입력: 변경 파일과 diff, 테스트·스캔 결과, 관련 요구사항. 구현자의 설명은 입력에서 제외하라(독립성).
- 관점: 정확성, 기존 시스템 충돌, 보안(CWE), 성능(N+1, 복잡도, 메모리), 장애 격리, 테스트 충분성.
- 출력: **PASS / REQUEST_CHANGES / BLOCK**과 근거. 자동 검사가 실패하면 AI 판단과 무관하게 BLOCK이다.
- API 키는 저장소 비밀 설정에 두고, 외부 기여 PR에서는 비밀이 노출되지 않게 하라.

### 14.4 가드레일 (프로젝트에 AI 에이전트·도구 실행 기능이 있는 경우)

- 에이전트·도구별로 읽기, 쓰기, 실행, 삭제, 네트워크, 배포 권한을 최소로 나누고, 권한 밖 요청이 차단되는지 테스트하라.
- 외부 입력(사용자 텍스트, 문서, 도구 출력)은 지시가 아닌 데이터로 취급하고, LLM 출력은 스키마로 검증한 뒤에만 사용하라.
- 배포, 데이터 삭제 같은 되돌릴 수 없는 작업은 사람 승인을 거치게 하라.
- 실행마다 토큰, 시간, 호출 수 예산을 두고 초과 시 안전하게 중단하라.

## 15. 문서와 실제 구현의 일치, 문제 해결 기록

구현 후 프로젝트 문서와 실제 코드를 비교하라.

확인 대상: README, 설치 방법, 실행 방법, API 문서, 아키텍처 문서, 설정 문서, 배포 문서, 테스트 문서, 보안 문서.

실제로 존재하지 않는 기능을 문서에 작성하지 마라. 실제로 검증하지 않은 것을 "검증 완료"라고 작성하지 마라. 필요한 문서를 실제 구현 결과에 맞게 업데이트하라.

### 15.1 기록의 핵심: 네 가지

README와 PR에는 "어떤 기술을 몇 개 썼는가"가 아니라 아래 네 가지를 남겨라.

| 항목 | 내용 |
|---|---|
| **1. 어떤 문제를 정의했는지** | 무엇이 문제였고, 어떻게 발견했고(측정값, 재현 방법), 근본 원인은 무엇인가 |
| **2. 왜 그 기술을 선택했는지** | 선택한 방법, 검토한 대안, 대안을 고르지 않은 이유, 감수한 트레이드오프 |
| **3. 어떻게 검증했는지** | 실행한 테스트와 명령, 부하·보안·장애 상황 검증 방법과 환경 |
| **4. 결과가 어땠는지** | Before/After 수치, 남은 한계와 리스크 |

### 15.2 PR 본문 형식

```
## 문제 (Problem)          무엇이, 어떤 조건에서, 얼마나 문제였나 (측정값)
## 원인 (Root Cause)
## 결정 (Decision)          무엇을 바꿨나
## 대안 (Alternatives)      무엇을 검토했고 왜 고르지 않았나
## 영향 범위 (Risk)          API·스키마·인증·설정·다른 서비스 영향
## 검증 (Verification)      실행한 명령과 테스트, 환경
## 결과 (Result)            Before → After
## 관련 요구사항              REQ-...
```

```
예)
문제:  GET /todos p95 840ms (Todo 1,000개, 태그 3개씩)
원인:  Todo마다 태그를 개별 조회 → 요청당 2,001 쿼리 (N+1)
결정:  태그·소유자를 일괄 로딩하도록 변경
대안:  캐시 도입 → 쓰기 시 무효화 정합성 문제가 새로 생겨 보류
검증:  쿼리 수 테스트(N=10/100/1000), 부하 테스트 200 RPS 5분, 2 vCPU·512MB 제한
결과:  2,001 쿼리 → 3 쿼리 / p95 840ms → 61ms
```

### 15.3 README에 포함할 것

기획서의 문서 요구사항과 기존 README 구조를 우선하되, 해당되는 경우 다음을 포함하라: 문제 정의, 아키텍처와 도메인 경계, 설계 결정과 트레이드오프, 보안(위협, CWE 판정 요약, 암호 선택), 성능(측정 환경, 부하 결과, 한계점, 개선 전후), **장애 시나리오**(의존성별 탐지 → 격리 → 복구 → 검증), 테스트 방법, 알려진 한계, 실행과 복구 방법.

## 16. 최종 요구사항 대조

작업 종료 전에 개발기획서를 다시 처음부터 끝까지 읽고 실제 구현 결과와 요구사항을 하나씩 대조하라.

다음 항목이 하나라도 남으면 완료를 선언하지 마라: 미구현 요구사항, 부분 구현, 테스트되지 않은 핵심 기능, 실제 환경에서 검증되지 않은 핵심 기능, 기존 기능의 regression, 실패하는 테스트, 남아 있는 임시 구현, TODO/FIXME, 문서와 코드의 불일치, 해결되지 않은 오류, 보안 요구사항 미충족, 명확한 설정/의존성 문제, **기존 시스템과의 미확인 충돌, 판정되지 않은 CWE 항목, 증거 없는 "검증됨" 상태**.

실제 환경 검증이 불가능한 핵심 항목은 그 제약과 대체 검증 결과를 보고하되, 해당 항목까지 최종 검증이 완료되었다고 선언하지 마라.

## 17. 최종 검증 순서

가능한 경우 다음 순서로 수행하라.

```
코드 검사 → lint → type/static analysis → unit test → integration test → end-to-end test
→ negative/edge-case test (정상·비정상·악성) → security test (CWE, 비밀정보·의존성 스캔)
→ DB 병목 검증 (쿼리 수, 실행 계획) → 성능·부하 테스트 (smoke → load → stress → soak)
→ 메모리 검증 → 장애 주입·복구 검증 → regression test → 실제 환경 검증
→ 독립 리뷰 (diff와 실행 결과만으로 재검토) → 문서 검토 → 요구사항 추적표와 실제 구현 비교
→ Git diff 검토 → Git status 확인 → build/deployment 검증 → CI/CD 검증
```

프로젝트에 해당하지 않는 단계는 무리하게 실행하지 말고 해당되지 않는 이유를 명확하게 판단하라. **해당 없음과 실행 불가를 구분하라.**

## 18. Git 변경사항 검토

작업 종료 전에 반드시 변경사항을 검토하라.

확인 항목: 의도하지 않은 파일 변경, 불필요한 코드, 디버깅 코드, 임시 파일, 비밀정보, 로그 파일, 빌드 산출물, 테스트용 데이터, 불필요한 의존성, 잘못된 설정, **테스트 약화(삭제, assertion 제거, skip 추가, 기준 완화)**.

불필요한 변경은 제거하라. 기존 사용자 변경을 작업 결과와 혼동하거나 임의로 제거하지 마라. 작업이 피처 브랜치에서 이루어졌는지, 기본 브랜치에 직접 반영된 변경이 없는지 확인하라.

완료 판단에는 16장과 아래의 세부 요구사항 검증 원칙도 함께 적용하라. 실행 불가 또는 검증 제한이 남은 경우 이를 숨기지 마라.

## 20. 자율 처리와 질문 기준

테스트 실패, 코드 오류, 통합 오류, 설정 오류, 실제 환경 오류, 의존성 문제, 예상하지 못한 edge case, 보안 취약점, 기존 기능 regression, 성능 병목, 장애 대응 미흡 등 스스로 해결 가능한 문제는 즉시 사용자에게 넘기지 마라.

**발견 → 원인 분석 → 수정 → 테스트 → 재검증**을 반복하라.

다음 경우에는 사용자에게 질문하라.

- 기획서에 서로 충돌하는 요구사항이 있는 경우
- 여러 구현 방식 중 어느 것도 요구사항을 만족한다고 판단할 수 없는 경우
- 외부 계정, 비밀키, 결제, 승인 등 사용자의 명시적 권한이 필요한 경우 (AI PR 리뷰어, 외부 스캔 서비스 도입 포함)
- 요구사항에 필요한 정보가 존재하지 않는 경우
- 기획서 범위를 크게 변경해야만 해결할 수 있는 경우
- 기존 시스템과의 충돌이 기획서 요구사항과 정면으로 부딪히는 경우
- 되돌릴 수 없는 작업(데이터 삭제, 파괴적 스키마 변경, 운영 배포)이 필요한 경우
- 테스트가 기획서와 어긋난다고 판단되지만 근거가 확실하지 않은 경우

그 외에는 합리적인 구현 방법을 선택하고 계속 진행하라.

## 21. 최종 보고 형식

모든 작업 후 다음 형식으로 실제 수행 결과를 보고하라. 이 항목은 AI가 개발 작업을 마친 뒤 작성할 보고 형식이며, 본 첨부 문서 자체가 개발 결과 보고서는 아니다.

| 항목 | 내용 |
|---|---|
| [구현 완료] | 구현한 주요 요구사항 / 변경된 주요 파일 / 주요 기술적 변경사항 / **기술 선택 이유와 검토한 대안**. 미완료 상태라면 이 제목을 "구현 현황"으로 바꾸고 완료로 오인하게 표현하지 마라. |
| [테스트] | 실행한 테스트 / 전체 테스트 결과 / 실패·경계 조건 결과(정상·비정상·악성) / regression 결과. |
| [보안] | CWE 판정 요약(적용·검증됨 / 해당 없음 / 미검증 개수와 주요 항목) / 스캔 결과 수치 / 암호 선택과 키 관리 방식. |
| [성능·부하] | 측정 환경 / 쿼리 수, p50·p95·p99, 처리량, 오류율, 메모리 추이 / 찾은 한계점과 병목 / 개선 전후 수치. 기획서 기준이 없으면 측정값만 보고하라. |
| [장애 격리·복구] | 주입한 장애와 결과(탐지 → 격리 → 복구 → 검증) / 검증하지 못한 시나리오와 사유. |
| [실제 환경 검증] | 실제 환경에서 검증한 항목 / 검증 결과 / 검증 불가 사유 및 대체 검증 결과. |
| [하네스 증명] | 예측한 시스템의 한계(신뢰성, 부하·병목, 가드레일) / 그것을 어떻게 지켜냈는지 / 증거 / 자동화한 검증(명령, CI, PR 리뷰). |
| [문서] | 업데이트한 문서 / 작성한 문제 해결 기록(문제, 선택 이유, 검증, 결과). |
| [Git 변경사항] | 주요 변경사항 / 브랜치 / commit 정보 / PR / CI/CD 결과. commit, PR 또는 CI/CD를 수행하지 않았다면 수행하지 않았다고 명시하라. |
| [미해결 사항] | 실제로 해결되지 않은 문제가 있는 경우에만 작성하라. 문제가 없다면 "미해결 사항: 없음"이라고 명시하라. |

"추후 개선할 수 있음", "향후 고려 가능" 같은 일반적인 개선 가능성은 미해결 사항으로 작성하지 마라. 미구현·미검증 핵심 항목과 실제 실행 제약은 별도로 명확히 공개하라.

## 필수: 세부 요구사항별 증거 기반 검증

요구사항 충족 여부를 단순한 키워드 검색, 파일 존재 여부, 함수 이름, 클래스 이름 또는 관련 코드의 존재만으로 판단하지 마라.

기획서 요구사항을 가장 작은 검증 가능한 단위까지 분해하고 각 요구사항에 대해 다음을 개별적으로 확인하라.

1. 요구사항의 정확한 의미
2. 실제 구현 위치
3. 구현이 요구사항의 전체 범위를 충족하는지
4. 정상 동작 테스트
5. 실패/경계 조건 테스트 (비정상·악성 흐름 포함)
6. 실제 환경 검증
7. 기존 기능 및 기존 시스템과의 충돌 여부
8. 문서와 실제 구현의 일치 여부
9. 위 각 항목의 증거(실행 명령, 결과, 위치)

모든 세부 요구사항이 확인되기 전에는 "완료", "100% 구현", "모든 요구사항 충족"이라고 보고하지 마라. 특히 키워드가 존재한다는 사실을 기능 구현의 증거로 사용하지 마라.

최종 완료 보고 전에 반드시 개발기획서를 다시 확인하고 실제 구현과 요구사항을 하나씩 대조하라.
